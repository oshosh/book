## 12.1 웹사이트 성능
  - 사용자들의 공통 기대 사항
    - 방문한 목적 손쉽게 달성
    - 방문한 목적 손쉽게 달성에 걸리는 시간이 짧아야 함
    - 개인정보 노출 등 보안 철저
  - 웹사이트의 성능과 사용자 경험 사이의 상관관계
    - 1초 내로 로딩되는 사이트는 5초 내로 로딩되는 사이트보다 전자상거래 전환율이 2.5배 높다
    - 0 ~ 5초의 범위에서, 1초 로딩이 늦어질수록 전환율은 4.42%씩 떨어짐
    - 페이지 로딩 시간이 0 ~ 2초 사이인 페이지에서 가장 높은 전환율을 달성
    - 소비자의 70%는 페이지 속도가 온라인 커머스 사이트를 방문하는 데 영향을 미친다
    - 절반 가까운 사람이 더욱 빠르게 로딩할 수 있다면 애니메이션과 동영상이 필요 없다고 밝힘

## 12.2 핵심 웹 지표란?
  - 구글에서 사이트에서 핵심적인 웹 지표
    - LCP(Largest Contentful Paint): 최대 콘텐츠풀 페인트
    - FID(First Input Delay): 최초 입력 지연
    - CLS(Cumulative Layout Shift): 누적 레이아웃 이동
  - 특정 문제 진단
    - TTFB(Time To First Byte): 최초 바이트까지의 시간
    - FCP(First Contentful Paint): 최초 콘텐츠풀 시간

## 12.3 최대 콘텐츠풀 페인트 (LCP)
  - 정의
    - **요소가 아무리 커도 화면 안에서 실제로 보이는 부분(뷰포트)만 LCP 크기 계산 대상이다.**
    - 페이지가 처음으로 로드를 시작한 시점부터 뷰포트 내부에서 가장 큰 이미지 또는 텍스트를 렌더링하는 데 걸리는 시간
    - 뷰포트 내부에서 `큰 이미지와 텍스트`는 다음과 같다.
      - `<img>`
      - `svg` 내부의 `<image>`
      - poster 속성을 사용하는 `<video>`
      - url()을 통해 불러온 배경 이미지가 있는 요소
      - 텍스트와 같이 인라인 텍스트 요소를 포함하고 있는 블록 레벨 요소
        - 이 블록 레벨 요소에는 `<p>`, `<div>` 등이 포함된다. 
        - 아래 요소들은 화면에 박스 하나를 만듬
          ```
          <div>
          <p>
          <section>
          <header>
          <article>
          <main>
          <h1> ~ <h6>
          ```
    - 의미
      - 웹페이지가 로딩이 완료되어 사용자에게 노출되기까지 걸리는 시간을 측정 할때 `DOMContentLoaded` 이벤트가 호출되는 시간을 생각 할텐데 `DOMContentLoaded`는 HTML 문서를 완전히 불러오고 파싱했을 때 발생하는 이벤트로, 페이지의 `document` 대상으로 일어나며 단 한번만 호출된다. 하지만 스타일시트, 이미지, iframe 같은 리소스는 아직 안 불러왔을 수도 있다. 그렇기 때문에 "페이지 준비 완료"라고 보기엔 부족하다. 반대로 `onload`의 경우는 전부 가져왔을때 실행됨
      - 사용자가 실제로 “로딩됐다!”라고 느끼는 시점 = 가장 큰 이미지나 텍스트가 화면에 그려진 순간 → LCP(최대 콘텐츠풀 페인트)
    - 기준점수
      - 2.5 초 내 응답 굿
      - 4초 이내 보통 그이상은 나쁨
    - 개선방안
      - 텍스트는 언제나 옳다.
      - 이미지는 어떻게 불러올 것인가? background-image 대신 img 태그를 사용하자 가장 빠른 성능을 보여줌
    - 조심 사항
      - 이미지 무손실 압축
      - `loading=lazy` 사용 주의: LCP에서는 크게 도움을 주지 않을 뿐더라 로딩 속도만 늦추게 된다.
      - `fadein`과 같은 각종 애니메이션
      - 프리로드 스캐너가 바로 읽을 수 있는 부분은 빠르게 가져가는것이 좋음
      - 같은 origin에서 가져오는것이 빠름 예를 들면 nginx에서 가져오는 것
        - 다른 origin에서 가져오게 되면 네트워크 커넥션을 다시 수행해야함.

## 12.4 최초 입력 지연(FID)
  - 정의
    - 사용자가 페이지와 처음 상호 작용할 때 응답으로 브라우저가 실제로 이벤트 핸들러 처리를 시작하기까지의 시간을 측정
  - 의미
    - 구글은 사용자 경험을 크게 4가지로 분류해 정의
      - `Response`: 사용자의 입력에 대한 반응 속도, 50ms미만으로 이벤트를 처리할 것
      - `Animation`: 애니메이션 각 프레임을 10ms 이하로 생성할 것
      - `Idle`: 유효 시간을 극대화해 페이지가 50ms 이내에 사용자 입력에 응답하도록 할 것
      - `Load`: 5초 이내에 콘텐츠를 전달하고 인터렉션을 준비할 것
    이는 `RAIL`이라고 부르며 `FID`는 `R`에 초점을 맞추고 있다.
  - 기준점수
    - 100ms 이내로 응답이 와야 좋은 점수를 얻을 수 있고, 300ms 이내인 경우 보통, 그 이후는 나쁨으로 처리된다.
  - 개선 방안
    - 실행에 오래 걸리는 긴 작업을 분리
      - 꼭 웹페이지에서 해야 하는 작업인가: 크롬 개발자 도구에서 네트워크 속도를 감속 시킨후에 테스트해본 뒤에 웹페이지에서 작업해야 하는 작업인지 고민해 봐야 한다.
      - 긴 작업을 여러 개로 분리하기: 하나의 긴 작업이 메인 스레드를 계속 점유할 수록 사용자는 페이지에서 응답을 받지 못하고 있을 가능성이 크다. 그렇기에 여러 개로 분리하는 것이 좋다.
    - 자바스크립트 코드 최소화
      - 사용되지 않은 코드가 얼마나 있는지 확인 여기서 확인된 코드들은 특정 이벤트에 따라 실행되는 코드, 예기치 못한 상황에서 실행될 코드 등 다양한 것들이 존재할 수 있는데 지연 로딩이나 우선순위를 낮춰서 불러오는 것이 좋다.
      
      - 폴리필 사용 시 인터넷 익스플로러 11 이하 버전에서는 지원하지 않는 메서드를 위해 꽤 용량이 큰 코드가 들어가지 때문에 경우에 따라 직접 구현하는게 좋을 수도 있음.
    - 타사 자바스크립트 코드 실행의 지연
      - async와 defer를 이용해 지연 불러오기를 사용하는 것이 좋고 async 보단 defer 가 좋다 하지만 전부 defer 사용은 불가할 수도 있음.

      | 속성        | 다운로드 시점             | 실행 시점                            | 실행 순서            |
| --------- | ------------------- | -------------------------------- | ---------------- |
| **async** | HTML 파싱과 *병렬로 다운로드* | 다운로드 끝나는 즉시 실행                   | **순서 보장 안됨**     |
| **defer** | HTML 파싱과 *병렬로 다운로드* | HTML 파싱 끝난 뒤(문서 parsing 완료 후) 실행 | **HTML 순서대로 보장** |


## 12.5 누적 레이아웃 이동(CLS)
